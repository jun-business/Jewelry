# Form B 계약 동의 · 단계별 취소·환불 — 운영 가이드 (D-24·D-25)

> 대상: 운영자(설정·링크 발송·본인 확인·환불 처리), 아버님(견적 고지 작성·발주 승인).
> 코드: `services/contracts.py`, `services/refunds.py`, `web/routes_contracts.py`, 매핑 `mappings/contract_v1.json`(v1.1), 폼 원본 `mappings/contract_v1_form.json`.

## 1. 흐름 한눈에

1. **Form A**(맞춤제작 문의) → 주문 접수 → 시안 → 아버님이 **견적 확정**.
2. 견적서에 **개별 주문제작 특성**과 **청약철회 시 예상되는 회복하기 어려운 손해 사유**를 적는다(견적 작성 화면 “개별 주문제작 고지” — 비어 있으면 링크를 만들 수 없음).
3. 주문 화면 › 시안·견적 탭 › **계약 동의(Form B)** › `계약 동의 링크 생성` → `링크 복사` → 카카오톡으로 고객에게 직접 보냄 → `고객에게 보냄 기록`.
4. 고객이 Form B에서 동의 항목만 고르고 제출(주문번호·견적번호·확인코드는 미리 채워짐).
5. 앱이 5분마다(또는 `계약 동의 상태 확인`) Form B 응답을 가져와 **자동 검증** → `관리자 검토 필요`.
6. 운영자가 **본인 확인·검증 완료**(확인 방법 + 근거 메모) → 문제가 없으면 **계약 유효** → 주문이 자동으로 “고객 동의 완료”.
7. 예약금 결제 요청 → 결제 확인 → **상세 CAD 착수**(Gate 1) → 최종 CAD 고객 승인 → **잔금 2/3 확인** → 아버님 발주(Gate 2) → 수령 → 검수 통과 → 발송(Gate 3).

| 구조 | 6개 섹션 · 9개 필수 문항(Q1~Q8 + Q6-1) · 응답자 이메일 **Google 인증 수집** | forms.get으로 확인(rev 00000079) |

| 게시 | **게시됨(2026-10-24 확인, 응답 받는 중)** | 게시를 끄면 고객이 “게시되지 않은 문서” 화면을 보고, 앱도 링크를 만들지 않음 |

## 3. 계약이 유효해지는 조건

모두 충족해야 `계약 유효`. 하나라도 아니면 자동 확정하지 않는다.

| # | 조건 | 실패 시 |
|---|---|---|
| 1 | Q1·Q2·Q3이 발행한 주문번호·견적번호·확인코드와 일치 | 주문번호·견적 불일치 → **재발행** / 확인코드가 다르면 응답을 어느 요청에도 잇지 않고 보관 |
| 2 | 고객 신원 확인 | 운영자 확인(기존 연락처·확인된 상담 채널 등). 전에 확인한 계약 이메일과 같으면 시스템이 대조해 표시 |
| 3~8 | Q4 견적·제작 조건 / Q5 예약금 1/3·잔금 2/3 / Q6 청약철회 관련 **별도 동의** / Q6-1 단계별 취소·환불 정책 확인 / Q7 배송·A/S 안내 확인 / Q8 최종 계약 동의 | “동의하지 않습니다” → **고객 거절**, “추가 설명이 필요합니다”(Q6-1·Q7) → **검토 대기**, 누락 → 검토 대기 |
| 9 | 견적이 발행 당시 버전 그대로 유효(대체·만료 아님), Form B 고지 문구·문항 버전이 발행 당시와 같음 | 새 견적 버전 → 이전 요청 자동 대체 · 고지 변경 → 재발행 |
| 10 | 운영자 검증 완료 | `검증 완료`를 눌러야 함(응답이 새로 오거나 수정되면 다시) |

- 운영자가 풀 수 있는 것: 본인 확인, 같은 내용 중복 응답 확인. **풀 수 없는 것**(재발행 필요): 불일치, 거부, 설명 요청, 누락, 고지 변경, 서로 다른 응답.
- 확인코드는 응답을 요청에 잇는 열쇠일 뿐 **본인 인증이 아니다**. 링크가 전달·유출될 수 있으므로 반드시 본인 확인을 한다.
- 확인코드와 링크 전체는 로그·감사로그·오류 문구에 남지 않는다(DB에는 해시와 암호문만).

## 4. 주문 화면에서 보이는 것

견적 확정 상태(견적번호 `Q00007-v1` 형식) · 링크 생성 여부·적용 정책 버전 · 링크 복사 · 고객 전달 기록 · 고객 제출 여부 · **동의 항목별 결과**(Q4·Q5·Q6·Q6-1·Q7·Q8) · 고객 식별 검증 · 최종 계약 유효 · `계약 동의 내역 보기`(증거 화면). 고객 화면에는 주문별 계약 동의 기록 목록이 있다(같은 고객의 주문마다 따로).

**증거 화면**(`/contracts/{id}`): 견적 스냅숏·HTML(+PDF)과 해시 검증, 개별 제작 특성·예상 손해 사유, 발행 당시 Form B 전체 고지 원문(청약철회 고지·단계별 환불 정책·배송/A/S 안내 포함), 적용 정책 원문, 응답 원본(JSON·해시·수정 이력), 문항별 독립 동의 기록, 본인 확인 결과, 검토·확정 담당자·시각, 고칠 수 없는 이력.
- 응답자 이메일은 가려서 보이고, **운영자만** `이메일 보기(기록 남음)`·`증거 내보내기(ZIP)`를 쓸 수 있다(감사로그 기록).

## 5. 취소·환불 요청 (Form B 03-1 단계별 정책)

주문 › 결제 탭 › **취소·환불 요청 접수**(사유 구분·접수 채널·고객 요청 시각·내용). 접수하면 ‘환불·취소 검토’ 문제가 열려 **상세 CAD 착수·발주·검수·발송이 막힌다**(취소 요청 뒤 착수를 기록하는 일 방지). 상세 CAD 착수 시각은 착수 버튼을 누른 서버 시각(감사로그)이라 고치거나 소급할 수 없다.

| 단계 | 판정(요청 시각 기준) | 자동 계산 | 법적 검토 |
|---|---|---|---|
| R1 | 결제한 금액 없음 | 0원(돌려줄 대금 없음) | 불필요 |
| R2 | 결제 후 · 상세 CAD 착수 전 | **예약금 전액**(틴틴골드 자체 정책) | 불필요 |
| R3 | 상세 CAD 착수 후 · 발주 전 | 없음 — CAD 비용을 **자동 공제하지 않음** | 필요(법정 청약철회 우선) |
| R4 | 발주 후 · 배송 전 | 없음 | 필요 — 개별 주문제작·회복 불가능한 중대한 피해·사전 별도 고지·전자문서 동의·실제 제조 진행과 손해 근거. **Form B 동의 하나로 판정하지 않음** |
| R5 | 배송 후 단순 변심 | 없음 — 자동 환불 거절 없음 | 필요(일반 청약철회 기간·주문제작 예외 요건) |
| R6 | 제품 하자·계약/표시와 다름 | 없음 · 배송비 기본 판매자 부담 | 필요 — **청약철회 제한 동의와 별개**(수령 3개월·안 날 30일 법정 철회권, 하자 권리 유지) |

처리 순서: (필요하면) `법적 검토 기록`(근거·법정 청약철회 해당 여부) → `환불액 결정`(사람이 금액·근거·배송비 부담) → 결제 취소·이체 → `환급 완료 기록`(실제 금액·방식·증거). 법정 청약철회(또는 R2)면 **환급 기한 = 기산일 + 3영업일**(공급된 상품은 반환받은 날, 미공급은 철회일; 주말·휴무일 제외)을 자동 계산하고 지나면 표시한다. 작업 진행 상황(시스템 기록)과 법적 검토 상태는 화면에서 따로 보인다. AI는 환불 거절이나 공제액을 정하지 않는다(코드상 분리).
