- **배치(SRS-160)**: 데이터 폴더 `%LOCALAPPDATA%\JewelryOS\<env>\` — `jewelry_os.db`, `files/`, `backups/`, `secrets.env`(icacls로 현재 사용자 전용), `logs/`. 웹 서버는 정적 자원(`/static/*`)과 인증된 라우트만 제공하며 데이터 폴더를 URL로 노출하지 않는다(`/data`, DB 파일 경로 = 404).
- **원칙 1 — 상태는 전이 서비스로만**(SRS-080): DB 트리거가 `transition_ctx` 토큰 없는 `lifecycle_state` UPDATE를 거부.
- **원칙 2 — 화면과 서버가 같은 차단 문구**(SRS-142): `domain/transitions.check()` → `list[Unmet(code, message, fix)]`. 화면 렌더와 409 응답이 같은 목록.
- **원칙 3 — 외부 쓰기 없음**(SRS-112): Google은 읽기 전용 범위(`forms.responses.readonly`, `drive.readonly`), 네이버·카카오는 Manual(사람 입력).

## 5. 모듈 간 인터페이스 🔒 (동결 대상 — RTM 7부)

### BD-001 상태·라벨·매핑 (`domain/states.py`)
- `S` 18값(PRD §8.1 16단계 + DECLINED·CANCELLED), `Phase` 6값, `PHASE_OF`(해석서 EXP-015), `QUEUES`·`QUEUE_STATES`(EXP-002 대응표; **“검토 필요” = 접수 3단계이면서 `동의 없음` 외의 보류가 없는 주문** — B-10), 라벨 사전(문자열 원본은 PDS §5.2).
- 결제 요청 상태: `DRAFT`(준비 중) · `LINK_READY` · `PAID`(결제 확인 대기 — 금액은 맞았지만 보류·이슈로 확인 전이가 막힌 상태, DD-002) · `PAID_VERIFIED` · `MISMATCH` · `CANCELLED` · `NOT_APPLICABLE`(잔금 없음 — FULL 정책 또는 잔금 0원일 때 화면에 표시되는 **가상 행**, DB 행은 만들지 않음).
- 이슈 상태: `OPEN` → `RESOLVED`(되돌림 없음, 재발 시 새 이슈).

### BD-002 전이 서비스 (`domain/transitions.py`)
```
TRANSITIONS: dict[action, T(action, frm: tuple[S], to: S|None, actors: set[Actor], label)]
check(ctx, order_id, action, actor, payload=None, submitting=False) -> list[Unmet]
perform(ctx, order_id, action, actor, payload, expected_version=None, effect=None) -> order_row
revert_check / revert_last(ctx, order_id, actor, reason)
system_perform(ctx, order_id, action)   # actors == {system}인 전이만
```
- `Actor` = `maker` | `operator` | `system`(actor=None). **system 전이는 `ingest_brief`·`to_review` 두 개뿐**(SRS-116). 새 디자인 업로드가 일으키는 `revalidate_design`(CUSTOMER_DESIGN_APPROVED→DETAIL_CAD)은 **업로드한 maker가 주체**로 감사에 남는다(B-11).
- `perform` 트랜잭션: 버전 확인(불일치 `ConflictError`) → `check(submitting=True)`(비어 있지 않으면 `TransitionBlocked`) → `transition_ctx` 토큰 → 상태 UPDATE(`version+1`, `state_entered_at`) → `effect(c, order)` → 감사 → 퍼널 → 커밋. 예외 시 전부 롤백.
- 차단 표 = SRS §3-1을 `BLOCKS`로 그대로.

### BD-003 조건 문구 카탈로그 (`domain/guards.py`)
- `Unmet(code, message, fix)`. 코드·문구의 원본은 PDS §5.4(G-WRONG-STATE·G-CONFLICT·G-ISSUE-RESOLVE 포함). G-WRONG-STATE는 화면에 버튼을 그리지 않는 경우의 서버 응답에만 쓴다.

### BD-004 저장소 계약 (`core/db.py`, DD-001)
- 쓰기는 `with db.tx() as c:`(`BEGIN IMMEDIATE`, 중첩 시 합류). 동시성 = SQLite 잠금 + UNIQUE.
- **낙관적 잠금(B-12)**: `orders.version INTEGER NOT NULL` — 모든 주문 상세 폼은 숨김 필드 `version`을 싣고, 서버는 `expected_version != 현재`면 `ConflictError` → **HTTP 409 + `G-CONFLICT`**(PDS E-15: 내 입력은 폼에 그대로 다시 렌더).
- 불변 트리거: `audit_events`·`payment_events`·`customer_acceptances` UPDATE/DELETE 거부, 승인 `quotes`·그 `quote_items` 변경 거부(`APPROVED→SUPERSEDED` 상태 변경만 허용), `orders.lifecycle_state`는 `transition_ctx` 필수.

## 6. 상태 전이와 모듈 사이 흐름

### 6.1 라이프사이클
PRD §8.1 + 해석서 EXP-014 표(BD-002 소유). 비전이 액션도 차단 표 대상: `build_packet`.

### 6.2 보류 사유(`services/orders`)
`NEEDS_INFO`·`WAITLISTED`·`HOLD`·`NO_CONSENT`. **동의 없음(B-10, SRS §3-1 NO_CONSENT 행과 일치)**: 동기화가 동의 없는 응답을 만나면 주문을 만들고 `NO_CONSENT` 보류를 붙인 뒤, AI 분석을 **실행하지 않고** 시스템 전이 두 개(`ingest_brief`·`to_review`)만 수행한다 — 차단 표의 “모든 진행 전이”는 사람 전이(PROGRESS 집합)를 뜻하며 시스템 전이는 포함하지 않는다(브리프 = “동의 없음 — AI 미실행”). 주문은 OWNER_REVIEW + 동의 없음 칩으로 “검토 필요” 큐에 보이고, 다음 조치 = “동의 증빙 기록”. 증빙 기록 시 보류 해제 → AI 분석 작업 등록.

### 6.3 이슈(`services/orders`, B-09)
| 유형 | 여는 경로 | 해결 조건(필수 입력) |
|---|---|---|
| PAYMENT_MISMATCH | 결제 입력 금액 합 ≠ 기대(자동) | 해결 방법(추가 결제 예정·금액 정정·취소 전환) + 사유. 해결 뒤 금액이 맞으면 결제 확인 자동 재시도 |
| REFUND_REVIEW | 결제 입력 상태가 취소·반품 요청/완료(자동) | 결과(계속 진행 / 취소로 전환 → 주문 취소 화면으로) + 사유 |
| DISPUTED | operator 수동 | 결과 텍스트 |
| DELIVERY_DELAY | 수동 또는 납기 위험 알림의 “지연으로 기록” | **새 예상일 + 고객 지연 안내 발송 기록(상담 초안 SENT 1건 선택 또는 증빙 텍스트)** |
| CHANGE_REQUEST | 수동(변경 내용·귀책 필수). **열 수 있는 단계: FREE_CONCEPT~CUSTOMER_DESIGN_APPROVED(발주 전)**. 발주 후 고객 변경은 REWORK(귀책 “고객 요청 변경”)로 기록 — 추가 비용은 별도 결제 요청 없이 operator 메모 + 잔금 정산에서 다룬다(R1 한계, TBD-007) | 새 견적 버전 승인 + 고객 재동의 기록 시 자동 해결, 또는 operator가 “변경 철회(고객 취소)”로 수동 해결 |

| REWORK | QC 불통과에서 “재작업 문제로 기록”(귀책 필수: 고객 변심 / 제품 하자 / 계약 사양 불일치 / 불명) | 판매자 귀책(하자·불일치)·불명 = 재작업 완료 메모 → 새 QC. **고객 변심 = 변경 주문(`change_orders`) 4단계(판정→추가 견적→고객 동의→추가금 결제 확인, 단계 CHANGE 결제 요청) 완료 후** 해결 → 새 QC. 변경 불가 판정이면 안내 후 해결(원래 사양) — r2, SRS-170 |

### 6.4 결제 요청(`services/payments`, B-06)
- `create_payment_req`(CUSTOMER_ACCEPTED, operator): 정책 THIRDS → `DEPOSIT`(예약금), FULL → `FULL`(총액). 같은 트랜잭션에서 단계 PAYMENT_PENDING.
- `record_payment`: 이벤트(PAID·CANCEL_REQ·CANCELLED·RETURN_REQ·RETURNED·UNPAID·REFUND) 추가. 같은 트랜잭션에서 해당 phase의 `PAID 합 − REFUND 합`을 계산: = 기대 → 해당 검증 전이(`verify_initial` 또는 `verify_final`) 수행 / ≠ 기대(PAID 입력) → PAYMENT_MISMATCH 이슈 / 취소·반품 → REFUND_REVIEW 이슈. **경계 불변식**: PAID_VERIFIED 요청이 있는데 단계가 PAYMENT_PENDING에 머무는 상태는 커밋되지 않는다.
- **잔금**: QC_PASSED에서 operator의 `create_balance_req`(비전이) — 금액 = 승인 견적 총액 − 확인된 예약금. FULL 정책 또는 잔금 0원이면 BALANCE 행을 만들지 않고 화면에 “잔금 해당 없음(NOT_APPLICABLE)” 가상 행. FULL이면 `verify_final_full`(operator 확인) = `verify_final` 전이.
- 시험 표지: 시험 운영 모드이거나 견적이 시험 견적이면 `is_test=1`.

### 6.5 변경 요청(B-07)
1. maker/operator가 CHANGE_REQUEST 이슈를 연다(변경 내용·귀책). 단계는 그대로, 차단 표대로 진행 액션이 멈춘다.
2. maker가 새 견적 초안(새 버전)을 작성 → `approve_requote`(이슈가 열려 있을 때만, 단계 CUSTOMER_ACCEPTED~FACTORY_SENT 이전): 새 버전 APPROVED, 이전 승인본 SUPERSEDED(보존).
3. `record_reacceptance`(증빙): 새 버전 고객 동의 → CHANGE_REQUEST 자동 해결.
4. 결제 영향: 단계 PAYMENT_PENDING이고 기존 예약금 요청이 미결제면 그 요청을 `CANCELLED`로 바꾸고 새 버전 기준 요청을 operator가 다시 만든다(UNIQUE는 quote_version 포함). 이미 확인된 예약금은 유지되고, 잔금 요청이 새 총액 − 확인된 예약금으로 계산된다. 새 총액 < 확인된 예약금이면 차액은 환불 이벤트로 operator가 입력.
5. 디자인 영향: 사양이 바뀌어 새 디자인을 올리면 6.6의 `revalidate_design`.

### 6.6 디자인·패킷
새 디자인 버전 업로드 → 유효 패킷 `VOID`(사유 “새 디자인 버전”) → 단계가 CUSTOMER_DESIGN_APPROVED면 같은 트랜잭션에서 `revalidate_design`(주체 = 업로드한 maker) → DETAIL_CAD. 경계 불변식: 패킷의 design_version_id ≠ 최신 디자인이면 FACTORY_SENT 불가(G-PACKET-STALE).

### 6.7 주문 취소(B-08)
`cancel`(operator, 활성 단계) — **같은 트랜잭션 부수효과**: 확인되지 않은 결제 요청(DRAFT·LINK_READY·MISMATCH)은 `CANCELLED`, 열린 이슈는 전부 `RESOLVED`(해결 내용 “주문 취소로 종료”), 유효 패킷은 `VOID`. 입력 = 사유(필수) · 증빙(필수) · **귀책**(판매자/고객 요청/불명, 필수) · **환불 결정**(전액 환불 / 일부 환불(금액·근거 정책 버전 필수) / 환불할 결제 없음) — “몰수”·“환불 불가” 선택지는 없다(SRS-164). 적용 정책 버전(견적에 고정된 수정·환불 정책)을 표시·기록. 실제 환불은 결제 탭에서 REFUND 이벤트(역분개)로 입력. 결제 이벤트는 삭제되지 않는다.

### 6.8 CS 초안
`DRAFT → APPROVED → SENT`, 고쳐 쓰기 시 `SUPERSEDED`(새 초안 생성). L3는 operator 판단 기록 후에만 maker 승인.
