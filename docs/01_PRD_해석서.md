## B. 해석서

### B-0. 제품 범주와 전체 여정
- **제품 범주**: 1인(+보조 1인) 주문제작 공방의 **로컬 백오피스/업무 관리 도구**(CRM + 주문 워크플로 + 승인 기록). 고객은 이 앱을 쓰지 않는다(고객 접점은 Google Forms·카카오톡·스마트스토어).
- **주 사용자**: 아버님(제작 책임자, 평일 저녁·주말 짧은 시간 사용). **보조 사용자**: 사업 책임자(운영자 — 정책·결제 대조·분석).
- **전체 여정**
  1. **처음**: PC에 설치 → 첫 실행 마법사(관리자 계정 2개, 정책 기본값, Google 연결 또는 Mock) → 빈 대시보드에 “첫 의뢰를 기다리는 중” 안내.
  2. **두 번째 이후(일상)**: PC 켜짐 → 자동 기동 → 밀린 응답 백필 → 아버님이 대시보드에서 “오늘 할 일”을 보고 주문 하나씩 처리 → 목록으로 돌아오면 필터·위치 유지 → 다음 주문.
  3. **실패·중단**: Google 권한 만료/네트워크 오류, AI 장애·비용 상한, 결제 금액 불일치, 네이버 취소와 제작 중 충돌, 세션 잠금, 공휴일·상한 초과.
  4. **복귀**: PC가 꺼져 있던 뒤(누락분 백필 표시), 주말 CAD 시작(이번 주말 CAD 대상), 잠금 해제 후 하던 화면 그대로.

### EXP-001 아버님 사용자 특성
- 출처: PRD-003 「아버님은 제한된 작업시간 안에 …」, §2 RACI 전반
- 압축 유형: 일반화된 사람(“아버님” — 연령·시력·디지털 숙련도 미기재)
- 구분: 암묵적 기대
- 경험 시나리오: 평일 밤 10시, 직장에서 돌아온 아버님이 안경 없이도 화면을 읽고, 영어 코드를 몰라도 무엇을 해야 하는지 안다.
- 관측 기준: Given 기본 설정 / When 어느 R1 화면을 열면 / Then 본문 글자 16px 이상, 보조 글자 13px 이상, 화면의 1차 문구에 영문 상태 코드(`OWNER_REVIEW` 등)가 노출되지 않는다(한국어 라벨, 코드는 보조 표기만), 글자 크기 “크게” 설정이 있다.
- 판정 방법: UI 자동 검사(최소 글자 크기 CSS 토큰) + 상태 라벨 사전 검사
- 상태: ASSUMED(ASM-002)

### EXP-002 “큐를 볼 수 있다” (FR-ADM-002)
- 출처: 「관리자는 신규·정보부족·수락·제작·지연·배송 등 큐를 볼 수 있다.」
- 압축 유형: 경계어(“등”) + 숫자 없는 구조
- 구분: 기저 동작 + 델타
- 경험 시나리오: 아버님은 “지금 내가 손대야 하는 것”만 모인 목록을 보고, 건수를 보고, 하나를 열어 처리하고, 돌아와도 같은 목록 같은 위치다.
- 관측 기준: Given 주문들이 여러 상태에 있음 / When 주문 목록을 열면 / Then 아래 큐 탭이 건수와 함께 보이고, 각 행에 주문번호·고객 표시명·상품·현재 단계·다음 조치·승인 상태·최종 변경이 보인다. 상세에서 뒤로 오면 선택 큐·검색어가 유지된다(URL 쿼리). 용어: 화면에서는 “주문번호”(`JOS-YYYY-NNNN`)로 통일.
- 큐 대응표(한 주문이 여러 큐에 동시에 속할 수 있고, 각 탭 건수는 그 탭 조건을 만족하는 주문 수 — “전체”만 중복 없는 활성 주문 수):

| 큐 | 조건 |
|---|---|
| 검토 필요 | 단계 INQUIRY_RECEIVED·AI_BRIEF_READY·OWNER_REVIEW 이고 `동의 없음` 외의 보류 사유 없음(동의 없는 주문은 여기서 “동의 없음” 칩과 함께 보임) |
| 정보 부족 | 보류 사유 `정보 부족` |
| 대기 | 보류 사유 `대기` |
| 시안·견적 | 단계 FREE_CONCEPT·QUOTE_APPROVED·CUSTOMER_ACCEPTED |
| 결제 확인 | 단계 PAYMENT_PENDING, 또는 QC_PASSED(잔금 확인 대기) |
| 제작 | 단계 INITIAL_PAYMENT_VERIFIED·DETAIL_CAD·CUSTOMER_DESIGN_APPROVED·FACTORY_SENT·FACTORY_RECEIVED |
| 지연·이슈 | 열린 이슈 1건 이상, 또는 EXP-007 알림 대상 |
| 배송 | 단계 FINAL_PAYMENT_VERIFIED·SHIPPED |
| 종료 | 단계 CLOSED·DECLINED·CANCELLED |
| 전체 | 종료 제외 전부 |

- “승인 상태” 열 = 현재 단계에서 다음으로 가기 위해 기다리는 승인 한 가지: `아버님 승인 대기` · `고객 동의 대기` · `운영 확인 대기` · `조건 미충족` · `—`(시스템 처리 중/종료).
- 판정 방법: 시험(목록 렌더 HTML 검사, 큐 건수 = DB 집계)
- 상태: ASSUMED(ASM-001)

### EXP-003 대시보드 “경고” (UI-01)
- 출처: 「UI-01 운영 대시보드: 신규/정보부족/수락 대기, 동기화/백업/결제 경고」
- 압축 유형: 숫자 없는 양(언제가 경고인가)
- 구분: 델타(임계값)
- 관측 기준: Then (폴링 간격 기본 5분) 마지막 성공 동기화로부터 **폴링 간격×3 = 기본 15분**을 넘으면 경고, 백업 마지막 성공 26시간 초과면 경고, **DB·파일 저장 드라이브** 여유 10% 미만이면 경고, 미해결 결제 이슈(PAYMENT_MISMATCH·REFUND_REVIEW, 시험 주문 포함) 1건 이상이면 위험 표시. 각 경고는 해결 화면 링크를 가진다. 카카오(수동 기록)는 동기화 경고 대상이 아니다.
- 판정 방법: 시험(시각 주입)
- 상태: CONFIRMED — H1 r1 Q5, 2026-10-17 (docs/DECISION_LOG.md)

### EXP-004 “명시적 승인”
- 출처: FR-ADM-003, FR-MFG-006, FR-Q-004, PRD-024 §8.3
- 압축 유형: 생략된 주체·방식(무엇이 ‘명시적’인가)
- 구분: 기저 동작
- 경험 시나리오: 아버님이 “수락”을 누르면 무엇을(어느 버전을) 승인하는지 요약이 보이고, 한 번 더 확인해야 승인된다. 실수로 미리 체크된 상태는 없다.
- 관측 기준: Given 승인 대상 / When 승인 버튼 → 확인 대화상자 / Then 대상 버전·조건 목록·승인자 이름이 표시되고, 체크박스는 기본 미체크, 거절·보류·상한초과 수락은 사유 필수. 저장 시 승인자·시각(KST 표시/UTC 저장)·사유·대상 버전이 감사로그에 남는다. 승인 권한은 역할로 제한된다(제작 승인 = 아버님 역할). **일괄 승인 기능은 없다.**
- 판정 방법: 시험
- 상태: ASSUMED(ASM-003)

### EXP-005 동시 진행 상한·대기 (FR-ADM-004)
- 출처: 「잠정 3건 초과 시 자동 수락 차단; 문의 저장은 계속.」, GATE-CAP-01 「자동 수락 금지/수동 검토」
- 압축 유형: 언급 없는 처리(상한일 때 사람이 수락할 수 있는가)
- 구분: 델타
- 관측 기준: **활성 수락** = 수락 이후이며 발송 전인 주문(단계 FREE_CONCEPT ~ FINAL_PAYMENT_VERIFIED; 공장 제작 중 포함 — O-02 보수적 제안). Given 활성 수락 3건(설정) / When 4번째를 수락 / Then 경고 대화상자에 “동시 진행 3/3”이 표시되고 **사유 입력 시에만** 수락(상한 초과 기록). 상한 도달 중에 새로 들어온 문의는 저장되고 보류 사유 **“대기”**가 자동으로 붙는다(표시일 뿐 수락·거절 아님). 아버님도 수동으로 “대기”를 붙이고 뗄 수 있다. 시스템은 어떤 경우에도 자동 수락하지 않는다.
- 판정 방법: 시험
- 상태: CONFIRMED — H1 r1 Q2(수정 — D-2), 2026-10-17 (docs/DECISION_LOG.md)
